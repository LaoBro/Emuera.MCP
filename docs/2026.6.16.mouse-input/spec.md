# CLI 鼠标点击按钮 — 实现规格

## 一句话总结

让终端用户用鼠标直接点击按钮文字来选择选项，不再需要先按 ↑ 进入键盘选择模式。

## 现状与问题

目前 CLI 模式下选择按钮的流程：

1. 游戏输出按钮文本，例如 `[0] Hello`、`[1] Quit`
2. 用户按 `↑` 键进入"按钮选择模式"
3. 底部出现提示 `> [1/2] [0] Hello | [Up/Dn] Switch [Enter] OK`
4. 用 `↑↓` 循环切换，`Enter` 确认

这要求用户理解"先进入模式再切换"这个两步操作，不够直觉。

## 目标

用户看到按钮文字后，直接用鼠标点上去就算选中，一步到位。

## 设计

### 核心思路

现代终端（Windows Terminal、iTerm2、xterm 等）支持"鼠标追踪协议"：程序告诉终端"我要接收鼠标事件"，之后用户每次点击，终端会把点击的行号、列号发给程序。

利用这个能力，我们做三件事：

1. **记住按钮位置** — 输出文本时，记录每个按钮在终端中的位置（第几行、第几列到第几列）
2. **接收点击** — 开启鼠标追踪，当用户点击时解析终端发来的坐标
3. **匹配并触发** — 点击坐标落在某个按钮区域内，直接提交该按钮的输入值

### 鼠标追踪始终开启

鼠标追踪在游戏启动时开启、退出时关闭，不做动态切换。原因：
- 游戏本身没有拖动、文本选择等需要"正常鼠标行为"的场景
- 始终开启让实现最简单，不需要跟踪状态变化

### 鼠标是主要操作方式，键盘是 fallback

- **鼠标**：直接点击按钮文字 → 立即提交
- **键盘**：保留现有 ↑↓ + Enter 模式，作为不支持鼠标的终端的备用方案
- 两者互不干扰，可以同时使用

### 点击行为

- 点击 = 直接提交，没有"先选中再确认"的两步流程
- 没有点击视觉反馈（点击后游戏会刷新画面，本身就是反馈）
- 没有悬浮高亮（留作后续增强）

### 不做什么

| 不做的事 | 原因 |
|---|---|
| 悬浮高亮 | 需要追踪鼠标移动事件，复杂度高，后续再做 |
| 点击动画/反馈 | 游戏画面刷新本身就是反馈 |
| 拖拽 | 游戏没有拖拽需求 |
| 鼠标模式动态开关 | 始终开启最简单 |
| pipe 模式鼠标支持 | stdin 重定向时没有终端，跳过鼠标初始化 |

## 涉及文件

- `Emuera.Headless/Agent/AgentCliProtocol.cs` — 主要改动文件
  - 启动时发送鼠标追踪开启序列
  - 退出时发送关闭序列
  - 输出时记录按钮终端坐标
  - 主循环中解析鼠标事件并匹配按钮

## 技术细节

### 协议选择

使用 XTerm 鼠标协议的两个模式组合：

- **1000**（基本鼠标追踪）：终端报告鼠标按下事件
- **1006**（SGR 扩展格式）：坐标以 `CSI < Cb ; Cx ; Cy M` 的明文数字形式发送，没有 223 列/行的坐标上限

开启序列：`\x1b[?1000h\x1b[?1006h`
关闭序列：`\x1b[?1000l\x1b[?1006l`

### SGR 鼠标序列格式

用户点击时终端发送：`\x1b[<0;X;YM`

- `0` = 左键按下
- `X` = 列号（1-based）
- `Y` = 行号（1-based）
- `M` = 按下（`m` = 释放，我们忽略释放）

### 按钮坐标记录

在 `FlushBuffer()` 输出文本前后采样 `Console.CursorTop`，结合 `displayLineList` 中当前代按钮的位置信息，记录每个按钮的 `(终端行号, 起始列, 结束列)` 到一个列表。

### 主循环集成

在 `RunConsoleKeyLoop()` 中，`Console.ReadKey()` 可能读到鼠标转义序列的首字节 `\x1b`。需要判断后续字符：
- 如果是 `[<` 开头 + 数字 + `M` 结尾 → 鼠标点击事件，解析坐标并匹配按钮
- 否则 → 普通按键，走现有逻辑

### 已知风险：Console.ReadKey() 与鼠标序列的兼容性

`Console.ReadKey()` 在 Windows 上底层调用 `ReadConsoleInput()`，会分别处理键盘和鼠标事件。但开启 XTerm 鼠标追踪后，终端（尤其是 Windows Terminal）会把鼠标事件转成 ESC 序列写入输入流，这时候 `ReadConsoleInput()` 可能把它当成键盘序列拆散，导致解析混乱。

**应对方案（按优先级）：**

1. **先试 `Console.ReadKey()`**：在 Windows Terminal 下测试，如果能正确分离键盘和鼠标事件，直接用
2. **回退到原始字节读取**：如果 `Console.ReadKey()` 有问题，改为在鼠标追踪开启时从 stdin 读取原始字节，手动解析 SGR 序列（`\x1b[<...M`）和普通按键，实现一个自定义的输入读取器
3. **最低限度回退**：如果以上都麻烦，就只在非 Windows 终端（Linux/macOS）启用鼠标，Windows 继续用键盘 fallback

这个风险需要在实现初期就验证，不要写完整体代码后才发现不兼容。

### 初始化与清理

- `RunConsoleKeyLoop()` 入口处：发送开启序列（仅当 `_ansiEnabled` 且非 pipe 模式）
- `RunConsoleKeyLoop()` 退出时（包括异常路径）：发送关闭序列
- pipe 模式（`RunPipeCliLoop`）：完全跳过鼠标相关逻辑
